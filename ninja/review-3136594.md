## 3\. P0 — critical defects still present

### 3.1 The rent-charge rate rule freezes the rate at assignment start — a defective model, now deliberate

**Commits:** `7ec6b27` (introduced), `3136594` (declared intentional and reinforced).

**What the code does.** `stall_assert_rent_charge()` (`sql/022_assignment_rent.sql`) resolves the booth rate as _the rate in effect at the assignment's start date_:

```sql
SELECT amount_minor INTO rate_minor
FROM public.booth_rent_rates
WHERE booth_id = booth_ref::uuid
  AND month_start <= assign_start          -- assign_start = assignment.starts_on
ORDER BY month_start DESC
LIMIT 1
FOR UPDATE;
```

The same predicate is used in `RentStore::rates()` (`src/Feature/Rent/RentStore.php`), `RentStore::facts()`, and the `payout_missing_rent` view (`sql/041_payout_run.sql`), and the rate-rewrite guard `stall_reject_rent_rate_rewrite()` (`sql/005_rent_charge.sql`) was rewritten to use it too.

**Status change since `38a3727`.** At `38a3727` I called this an inversion. The `3136594` commit message now states it plainly: _"Freeze the assignment-time rent rate."_ So it is no longer an accident. I am not withdrawing the finding — I am re-classifying it: **this is now a documented design decision that is wrong for an enterprise rent ledger.** Two empirical proofs, run this session against a live tenant (each inside a rolled-back transaction):

**(a) A rate set after the assignment starts makes rent unchargeable.** The normal workflow is _assign the booth, then set the monthly rate_:

```
assignment starts_on = 2026-01-01; rate set for month 2026-06-01
chargeAmount for 2026-06 THREW: a rent charge requires the booth rate from the assignment
```

Rent simply cannot be charged. This is the ordinary case, and it is the case the fixtures had to be _rewritten to avoid_ — see below.

**(b) A mid-tenancy rate raise is silently ignored.** The landlord raises the rent from $100 to $150 effective 2026-07-01:

```
rate at 2026-01-01 = 10000 (the assignment-time rate)
rate at 2026-07-01 = 15000 (a mid-tenancy increase)
chargeAmount for 2026-07 = 10000  <-- expected 15000 if the raise applies
```

The raise has **no effect**. `booth_rent_rates` is a monthly schedule keyed by `(booth_id, month_start)`; under this rule the `month_start` column is effectively dead — only the single latest row at-or-before the assignment start ever matters. You cannot raise rent on an existing tenant through the rate schedule at all.

**Why it is a design defect, not a defensible choice.**

1.  A monthly rate table whose month dimension is inert is a contradiction. If rates are meant to be frozen per lease, the table should be keyed by assignment, not by month.
2.  The only lever left to change rent mid-lease is the per-assignment `assignment_rent` override. That is workable but non-obvious, undocumented in the UI, and it means the _rate register_ and the _override_ are two competing mechanisms for the same fact.
3.  The tests were **bent to fit the rule.** `OwnerJourneyTest` was changed this session to set `month_start => ProbeMall::PERIOD_START` (`2020-01-01`) instead of `POSTING_DATE` (`2026-06-15`) — i.e. the test had to move the rate _before_ the assignment to make the charge work. `RentChargeTest` now asserts `4800` for a 2026-06-15 charge (a 16/30 proration of a rate set at 2026-06-01). When the fixtures must be reshaped to satisfy a rule, the rule is fighting the workflow.
4.  The rule was introduced by `7ec6b27`, whose title is "Read the check and the rent still owed from the payout pack" — the rate change was a _side effect_ of an unrelated commit, then rationalised after the fact.

**Enterprise bar.** The rate that applies to a charge is the rate in effect **on the charge date** (with a documented proration for a mid-month move-in). The correct predicate is `month_start <= date_trunc('month', <charge date>)`. If the intent really is a lease-frozen rate, then the rate must live on the assignment and the monthly table must be removed — and the UI must expose the override as _the_ way to change rent. Either way, the current state — a monthly schedule that is frozen at assignment start, with no UI path to change rent — is not world-class.

**Also still inconsistent.** `RentStore::uncharged()` enumerates candidate months with a _different_ predicate (`assignment.starts_on <= (rate.month_start + interval '1 month - 1 day')`), so the "what can I charge" list and the "what the charge trigger accepts" rule are defined in two places. It is currently masked because `uncharged()` re-resolves each line through `facts()`, but two definitions of the same business fact remain a latent defect.

### 3.2 GET requests still write to the database

**Commit:** `7ec6b27` (untouched by the two new commits).

`PayoutStore::quote()` (`src/Feature/Payout/PayoutStore.php:46`) and `PayoutStore::debtors()` (`:153`) both call `PayoutRunStore::ensureDraft()` (`src/Feature/Payout/PayoutRunStore.php:100`), which either `UPDATE`s `payout_runs.posting_date` or **`INSERT`s a new draft `payout_runs` row**. Both are on read paths: the vendor page (`PartyController::showRecord()`), the rent page (`RentController::render()` builds `'debtors' => … $this->payouts->debtors($today)`), and now also the new collect form (`RentReceipt::figure()` → `packFigure()` → `quote()`).

**Reproduced live this session** against a window with no draft:

```
window: 2027-12-01 .. 2027-12-31
drafts for this window before quote(): 0
quote() (a READ path used to render the payout page) returned: run 01a10d02-…
drafts for this window after quote(): 1
```

Merely viewing a page creates a payout run. This violates GET semantics (safe, idempotent, cacheable), pollutes `payout_runs` with rows nobody asked for, and lets a page render fail with a write error or lock conflict.

**Enterprise bar:** reads read. If a draft must exist to compute a quote, create it explicitly (a "start payout" action) or compute the quote from a view that does not persist a run.

### 3.3 `ensureDraft()` still creates duplicate draft runs under concurrency

**Commit:** `7ec6b27` (pattern predates it; the GET callers make it reachable).

`ensureDraft()` (`src/Feature/Payout/PayoutRunStore.php:100-119`) is a bare `SELECT … WHERE status='draft' AND window` followed by `INSERT` if empty. There is **no row lock and no unique constraint** on the draft window. `payout_runs` carries only `PRIMARY KEY (id)`, `UNIQUE (book_id, id)`, `UNIQUE (book_id, run_no)` — confirmed live from `\d payout_runs`. Two concurrent callers that both find no draft both `INSERT`.

**Reproduced live** with 10 parallel processes released from a shared wall-clock barrier (`probe_draft_barrier.php`):

```
=== drafts grouped by window (tenant webprobe) ===
 kind  | sales_from |  sales_to  | rent_month | drafts
-------+------------+------------+------------+--------
 batch | 2027-04-01 | 2027-04-30 | 2027-05-01 |      4
```

Four live draft runs for one window. Combined with §3.2 (every page view calls it), this is reachable from ordinary traffic.

**Enterprise bar:** guard the window with a partial unique index (`… WHERE status = 'draft'`) plus `ON CONFLICT`, or take an advisory lock as the ledger already does for `posting_key` (`stall_reject_live_posting_key`).

### 3.4 `PayoutSettler::settle()` still does not reconcile against a source of truth

**Commit:** `7ec6b27` (untouched).

`settle()` takes `int $applied` straight from the pack (`close()` passes `$row['settled']`), debits `vendor_payable` by that figure, then walks the ledger's open booth rent (`PayoutStore::boothRent()`) crediting each booth `min(left, open)`:

```php
if ($left !== 0) {
    throw new DatabaseRefusal('the settlement does not match the open booth rent');
}
```

This is a **post-hoc assertion, not a reconciliation**. The amount to settle is decided by the pack (a view); the ledger is then checked to agree, and a mismatch aborts the run with a generic error. The check is also asymmetric: it fires only when the ledger holds _less_ open rent than the pack claims. If the ledger holds _more_ (a rent charge landed between the pack read and the settle), the surplus is silently left open with no error. The "source of truth" is the same projection being validated, so a projection bug validates itself.

**Enterprise bar:** one authority. Either the ledger is authoritative (read open rent, settle `LEAST(payable, open rent)`, assert the pack matches) or the pack is (settle the pack figure, assert the ledger equals it). Right now the pack is authoritative and the ledger is a soft check — the weaker arrangement.

### 3.5 Tenant wipe is still broken by the append-only backup guard — no offboarding path

`bin/wipe-tenant.php` (`wipeTenant()`, line 21-23) does:

```php
$pdo->exec('DELETE FROM platform.owner_backups WHERE tenant_id = (SELECT id FROM platform.tenants WHERE slug = …)');
```

`platform.owner_backups` carries `owner_backups_append_only` (`BEFORE UPDATE OR DELETE`, `tgenabled = 'A'` i.e. `ENABLE ALWAYS`). Reproduced live this session:

```
$ DELETE FROM platform.owner_backups WHERE tenant_id = (SELECT id FROM platform.tenants WHERE slug='webprobe-38a');
ERROR:  a backup record cannot be updated or deleted
CONTEXT:  PL/pgSQL function platform.reject_owner_backup_mutation() line 3 at RAISE
```

Once a tenant has taken a single backup it can **never** be removed by the tooling. The only workaround found (again this session) was renaming the tenant (`UPDATE platform.tenants SET slug='webprobe-38a'`), which leaves the schema and role orphaned and accumulating. `bin/seed-dev-tenant.php` and `bin/prepare-race-tenant.php` inherit the breakage.

**Enterprise bar:** an offboarding path is table stakes for a multi-tenant platform. Either backups are genuinely immutable (then the wipe must drop the tenant's schema/role and _retain_ the backup rows, and the code must say so) or the guard must exempt a controlled administrative delete. The current state is a contradiction: the platform treats backups as immutable, the ops tool assumes it can delete them.

### 4.4 The `quoted()` identifier guard is still loosened

`InventoryStore::quoted()` (`:287`) and `BrandStore::quoted()` (`:121`) still use the permissive pattern introduced at `38a3727`:

```php
$part = '(?:"[a-z_][a-z0-9_]*"|[a-z_][a-z0-9_]*)';
```

This feeds `SELECT DISTINCT <col> FROM <relation>` in `InventoryStore::referenced()`. A whitelist against `pg_attribute`/`pg_class` (or `quote_ident` on both sides and compare) would be strictly safer. Low likelihood, but it is the wrong shape for a security boundary.

## 5\. P2 — medium / low (carried forward and extended for the new surface)

**New surface — rent receipt / tender flow (`4e3d524` + `3136594`).** The new flow (`RentPosting`, `RentReceipt`, `RentSlip`, `sql/043_rent_receipt.sql`) is, on the whole, well built: the tender rule is enforced in _both_ PHP (`RentPosting::tenders()`) and a deferred constraint trigger (`stall_assert_rent_payment()`), the check-number requirement is enforced in both layers, the receipt debits the open drawer and credits the booth receivable, and change is computed server-side (`RentSlip::change()`). Observations below are refinements, not defects:

-   **Check numbers are not deduplicated for received checks.** `stall_reject_duplicate_disbursement_check()` (`sql/041_payout_run.sql:220`) enforces uniqueness only for `source_type = 'check_disbursement'` (checks you _write_). A rent receipt's check number (`source_type = 'rent_payment'`) is not deduplicated, so the same check number can be entered on two receipts. Arguably acceptable (received checks can legitimately repeat), but for reconciliation a duplicate number against the same vendor is a fraud signal worth at least a warning.
-   **`sql/006_rent_payment.sql` is now a no-op.** The file was gutted to `DO $$ BEGIN NULL; END $$;` and the trigger moved to `sql/043_rent_receipt.sql` (which is idempotent and `CREATE OR REPLACE`s the function). This is correct on a fresh install (043 runs after 006) and on an upgraded one (the existing trigger is re-pointed to the new body), but it means the file named "rent\_payment" no longer defines rent payment — a migration-ordering trap for the next reader. A comment exists, which mitigates it.
-   **`?tendered=` is reflected onto the receipt.** `RentController::payment()` appends `?tendered=…` and `slip()` reads it to show change. The value is escaped through `View::text`/`View::money`, so it is not an XSS vector, but a query parameter that alters a printed financial document is a smell; the change belongs on the persisted journal, not in the URL.
-   **`debtors()` still joins on booth _code_, not id.** `src/Feature/Payout/PayoutStore.php:163` — `LEFT JOIN booths AS booth ON booth.code = pack.booth`. Joining on text rather than the id is fragile if codes are ever non-unique or re-cased. Unchanged.
-   **`payout_missing_rent` and `payout_pack` filter on `vendor.active`.** `sql/041_payout_run.sql` — `JOIN vendors AS vendor ON vendor.active`. An inactive vendor's payable and rent simply disappear from the pack and from missing-rent detection. An inactive vendor with an outstanding balance is invisible to the payout machinery. Unchanged.
-   **`Money::parseMinor()` is unsigned and unbounded.** `src/Ledger/Money.php` rejects zero and negatives and accepts `\d+` with no length cap; a very long digit string saturates `(int)` and the `* 100` can overflow to float. Fine for the amount fields it serves, but it is the only money parser and would be silently wrong for any signed field (refund, variance, negative adjustment) if one is wired to it.
-   **Backup DB password appears in process argv.** `PostgresTools::command()` (`src/Feature/Backup/PostgresTools.php:52`) builds `['docker','exec','-i','-e','PGPASSWORD=' . $connection->password, …]`. `proc_open` with `bypass_shell` and an argv array means no shell-injection risk, but the password is visible to any local user via `ps`/`docker inspect`. The non-docker path (`:92`) correctly uses the environment. Redaction only scrubs error text, not the argv.
-   **`checkCsrf()` failure renders a bare string.** `OwnerGate::checkCsrf()` writes `echo 'The form expired…'` with a 400 and no layout, and does not log the tenant. Minor UX/observability.
-   **`prove:race` is slow enough to time out.** Running green it exceeds a 60s synchronous budget and had to be backgrounded; the race harness has no per-proof timeout budget, so one slow proof stalls the whole gate.

## 6\. Governance root cause — why the regressions landed

`​.cursor/rules/do-not-run-tests.mdc` (added in `268104f`, `alwaysApply: true`):

> Do not run tests, proofs, or check commands unless this message asks for that run. This overrides `maintain-proven-level` and `prove-before-advance`.

`​.cursor/rules/maintain-proven-level.mdc` and `​.cursor/rules/prove-before-advance.mdc` were both amended to defer to it ("Do not start this run unless the user asked for tests or proofs in this message").

The effect is mechanical: the agent is forbidden from running `composer check` unless the message explicitly asks, so `7ec6b27` and `38a3727` were committed **without ever executing the gate they are measured against**. Six regressions — including one that broke the core rent workflow — shipped because the only feedback loop that would have caught them was switched off. The rule that defines "done" and the rule that forbids checking "done" are in direct conflict, and the one that forbids wins.

**Enterprise bar:** a change is not done until the gate that defines done has run on that change. If the goal is to stop runaway test loops, bound the run (one `composer check` per commit, with a timeout) — do not forbid it.

## 7\. What was checked and found sound (to bound the review)

Stated so the reader knows these were examined, not skipped: the append-only kernel (`ENABLE ALWAYS` triggers, event triggers rejecting trigger tampering, deferred constraint triggers); `posting_key` idempotency is genuinely enforced by `stall_reject_live_posting_key` under an advisory lock, with supporting index `journals_book_key_lookup`; `LedgerStore::commitJournal` transaction / `SET CONSTRAINTS` handling; `OwnerGate` password verification (`password_verify`), session-fixation defence (`regenerateId(true)`), and CSRF (`hash_equals`); `View::text` output escaping (`ENT_QUOTES | ENT_SUBSTITUTE`, UTF-8) with no raw user-data echoes found; register over/short variance sign handling; `CommandProcess` shell-injection safety (`bypass_shell` + argv array); `VendorRoster`/`BoothRoster` are pure in-memory projections (no N+1). The new rent receipt/tender flow is double-guarded (PHP + deferred trigger) and posts a balanced journal. The ledger kernel remains the strongest part of this codebase; the remaining defects are in the feature layer (GET-writes, draft race, settle self-check, offboarding) and the process around it.

## 9\. Recommended order of repair

1.  **Decide the rent-rate model and make it coherent.** Either (a) the rate is the rate in effect on the charge date — change the predicate to `month_start <= date_trunc('month', <charge date>)` in `sql/022_assignment_rent.sql`, `RentStore::rates()`, `RentStore::facts()`, `sql/005_rent_charge.sql`, and `payout_missing_rent`; or (b) the rate is genuinely frozen per lease — then move the rate onto the assignment, drop the monthly table, and expose the override in the UI as _the_ way to change rent. Re-run the proof suite and `prove:race` to green. (The current "monthly table frozen at assignment start" is neither.)
2.  Move draft-run creation out of GET render paths; add a partial unique index on the draft window (`… WHERE status='draft'`) plus `ON CONFLICT`.
3.  Make `settle()` reconcile against one authority, not a self-check.
4.  Give the tenant wipe a real offboarding path that respects the append-only backup guard.
